## Shared behavior decisions

These apply throughout the three chunks and do not form a fourth implementation project.

**Plan and snapshot identity.** Store basis, scope, target identity, proposed values, override status, and originating snapshot together where the existing code permits. Derive instructions and previews from that same proposal. Refresh must not overwrite an in-progress edit silently. If source conditions change, mark the proposal as needing review and use the existing server preview/compare-and-set checks before applying. Missing facts remain missing rather than becoming zero or example data.

**Saved-state migration.** Preserve existing import overrides (`ba_import_set_v2:<character>`), order marks (`ba_order_marks_v1:<character>`), and staffing notes (`SP_ROSTER_STORE`). Legacy import overrides have no recorded planning basis: load their chosen value as an override with an unknown basis and show Needs review before execution. Legacy ticks remain Marked by you, never Applied or Confirmed. Use an explicit, tested identity mapping when moving records to the new schema; do not silently discard user values or assign them an inferred basis. Preserve legacy records until migration succeeds, and keep unavailable or unmatchable records from being attributed to a different company or action. Respect existing reconciliation rules for obsolete notes and handle unavailable storage. Test migration from the existing v1/v2 stores and the staffing store.

**Three meanings of done.** `Marked by you` is a reversible local note with an outlined grey tick. `Applied · awaiting refresh` is blue and requires an actual successful supported write response. `Confirmed` is solid green and requires later source evidence matching that action's postcondition. A hidden finding, changed filter, pending request, or button click cannot establish confirmation. Preserve error/refused outcomes explicitly. For this redesign, automatic confirmation is limited to the current supported write families: import settings, shop and office scheduling, and hire/move in chunk 2, and missing uniforms in chunk 3. Chunk 2 records a short postcondition table defining the target identity, expected fields, and later-snapshot evidence required for each family; chunk 3 completes the uniform entry. Hire/move results retain the current-main partial/refused distinctions and have no undo. Reuse existing read-back checks where suitable. Every other action remains a manual note using the existing reconciliation behavior; do not build new verification engines for routes, purchases, or factory hours. Confirmation of an import setting is not proof that an existing stock gap or dependent factory change is resolved. Recurring and catch-up actions have independent state. Progress is keyed by character, target, action, and relevant proposed values; materially changed recommendations make old marks stale rather than silently completing the new plan. Preserve a way to clear local notes.

**Context and return.** All entry paths use the same route/context helpers. A finding carries its relevant site, product/contract, evidence target, and origin. Preserve ordering while the player is working in an open findings list and announce new arrivals on refresh rather than inserting them above their place. Retain the severity filters, expanded-list state, open Details, and destination scope across Back/Forward and reload through the route/history state design. Return restores filters, expanded details, and position while the origin still exists; when refreshed data removes it, restore the surrounding list and explain the changed state. Do not force every return to the top or keep a vanished row looking unresolved merely to preserve position.

**Visual and interaction consistency.** Use Archivo for body text and IBM Plex Mono selectively for numbers/compact labels; preserve the approved palette, thin rules, green accents, meaningful stock/hour/satisfaction visuals, and playful brand details. Avoid fixed artboard dimensions in production. Details, review, manual instructions, and Apply have separate roles and accessible names. Focus follows dialogs and navigation predictably and returns when closed. Status uses text/symbols as well as color. Measure contrast; verify real text enlargement, touch controls, and reduced motion. Decorative motion must not restart on every refresh.

**Runtime contracts.** Preserve `PAGE_DRAWS`/stale-page rendering behavior so snapshots do not redraw every page or reset open dialogs. Update route, finding, evidence, supply and search registries together. Keep frozen preference migration defaults intact. Scope CSS to avoid existing global collisions; use unique embedded-script names across the board, map and wiki. Use body-mounted popovers where sections clip positioned content. The CLI and Pyodide must continue sharing the board; do not introduce import-time dependencies on files absent from the worker filesystem.

## Execution and validation

Give each chunk one implementation owner and one isolated worktree with explicit file ownership. These chunks overlap heavily in `ba_dashboard.py`; integrate them sequentially rather than assigning concurrent edits to that file. Create a dedicated integration branch, for example `codex/ui-redesign-integration`, from current `origin/main`. Integrate completed chunks there and keep the incomplete migration out of `main` and public deployment. Later chunk worktrees include the integrated preceding chunks. At the start of each chunk and before the final PR, integrate current `origin/main`, resolve source conflicts and rebuild generated files, and reconcile newly added capabilities against the coverage ledger. Only the completed migration is proposed for merging to `main`; chunk reviews can target the integration branch. Preserve unrelated work in every checkout. A chunk can contain several commits without being fragmented into independent projects. This plan does not authorize commits, pushes, or deployments by itself.

Run the repository's required checks for the files actually changed. For the shared template this means `python -m unittest discover -s tests`, `node --test tests/*.test.cjs`, and `python build_web.py`. Landing `BANNER`/`BEFORE_SCRIPT` changes require building before the landing/news/release/privacy checks, as specified in `AGENTS.md`. Include map/finder, wiki, localization, and game-link checks when those surfaces change. If community files change, run `npm run test:community` and `npm run check:worker`. Update tests that depend on moved source anchors while retaining their behavioral assertions.

Regenerate generated assets from source. If the installed game is unavailable, use `python build_web.py --check` to assess consistency and record the limitation; it is not a substitute for rebuilding changed sources. Before release, test the actual rebuilt browser artifact as well as the CLI-generated board, including the existing `BOARD_TARGET=web` test path. Follow the current architecture registries and contributing/release rules. Write one accurate user-facing redesign changelog entry when the complete capability is ready, rather than announcements for mechanical intermediate work.

Use synthetic fixtures for automated tests, covering small and large companies, missing history/data, factories and no factories, multiple sites/types, both planning bases, manual sources, and game-link capability/error states. Add meaningful journey regression coverage for proposal consistency, company isolation, source refresh, old links, and return context. Do not add real saves to fixtures or issues. Record desktop/narrow/phone, light/dark, keyboard, enlarged-text and measured-contrast results per chunk; run a physical-phone check before release when a device is available, and report it as outstanding if not performed.

Agent click-throughs can verify routes and state; they do not demonstrate human discoverability. Before release, ask new and experienced players to perform three brief tasks without Search or coaching: find and review an import fix, locate factory running-hours planning, and find prices for a named shop. Observe first clicks, completion, confusion, and return behavior. Fix consequential navigation misunderstandings rather than running another open-ended visual redesign.

The finished handoff includes the updated coverage ledger, route aliases, concise validation evidence and outstanding limitations, and the coherent generated build. Release and rollback follow the existing project process, with a complete prior build available and persisted preferences/history preserved. No new deployment or feature-flag infrastructure is required for this redesign.
